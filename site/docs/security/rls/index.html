Row-level security (RLS) and tenant isolation

Two separate concerns: protecting CoFlow data and guiding RLS-sensitive application changes.

RLS inside CoFlow

The PostgreSQL tenant implementation uses forced row-level security on protected tables, with organization ownership and server-resolved project scope. Application authorization checks also apply. Organization isolation alone does not grant access to every project.

Verified identity establishes transaction-local app.organization_id and app.authorized_projects. Caller-supplied tenant headers are not an authorization source. Organization context without authorized project scope exposes no project records under the project-aware policies.

Runtime requirements

  • Use a restricted application role that does not own protected tables, is not a superuser, and cannot bypass RLS.
  • Backfill existing rows to verified organization/project ownership before activation.
  • Apply reviewed migrations through a separate authorized migration role.
  • Set transaction-local context for API, MCP and worker database operations, including after commits.
  • Verify missing-context denial, cross-tenant read/write denial and pooled-connection reuse against PostgreSQL.

SQLite development tests do not prove PostgreSQL RLS behavior. Startup guards check schema and role requirements; behavioral isolation tests remain necessary.

RLS in applications built with CoFlow

Use CoFlow to give coding agents approved RLS requirements before they change a protected route, migration or background job. Add an acceptance contract that covers both allowed and denied behavior.

Example rule: tenant-scoped invoice access

Resolve the organization from verified identity. Set its context in the query transaction. Require project authorization. Never treat possession of an invoice ID as permission.

This is engineering guidance for your implementation. CoFlow does not install, enable or certify RLS policies in your application merely because a rule is approved.

A useful acceptance checklist

  • Tenant A can read and update its own authorized records.
  • Tenant B cannot read, update, insert into or delete Tenant A’s records.
  • Missing organization or project scope fails closed.
  • Connection reuse does not retain another tenant’s context.
  • Workers and evaluations use the same authorization boundaries as API requests.
  • Cache, search and vocabulary results remain tenant and project scoped.

Source includes dedicated PostgreSQL RLS tests, including Workflow Studio isolation with a restricted non-bypass role. Confirm the evidence for the exact release deployed to your environment.
