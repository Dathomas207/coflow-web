Quickstart

Put your team’s standards in front of a coding agent, check a change and see a rule proposal, on your own repository.

Install the CLI

The local workflow needs no account, no server and no model key. CoFlow is a Python package with a coflow command. Install it into its own virtual environment from the source your onboarding contact gives you, then check that the command works:

python3 -m venv ~/coflow-env
~/coflow-env/bin/pip install <package source from onboarding>
export PATH="$HOME/coflow-env/bin:$PATH"
coflow --help

coflow --help lists init, validate, scan, compile, export, check, inbox and the other commands. The commands are written for macOS and Linux.

Initialize a repository

cd ~/src/your-repo
coflow init
coflow validate
coflow compile --paths app/main.py

init reads your manifests (for example pyproject.toml, package.json or alembic.ini), prints the packs it chose, copies them to .coflow/rules/, writes .coflow/config.yaml and generates AGENTS.md, the Copilot instructions, the Cursor rules and the agent skills. Choose packs yourself with --packs, or a named set with --bundle.

compile prints the rules an agent gets for that path, cut to the token budget. Commit .coflow/ and the generated files so the whole team gets them.

Connect your coding agent

coflow connect claude --dry-run
coflow connect claude

Name your client: claude, cursor, vscode (GitHub Copilot), codex, gemini, windsurf, cline, zed, jetbrains, amazonq, roo or aider. coflow connect --all connects every client whose own files are already in the repository. --dry-run prints the diff of each file first.

connect writes the client’s rule files and merges a coflow server into the client’s project MCP file, keeping every other server there. Windsurf, Cline and Zed keep MCP servers in a user-level file, so for them it prints the entry to paste. Aider has no MCP client and gets rule files only.

The local MCP server needs no token. To use the hosted service instead, add --hosted; the client then reads your credential from the COFLOW_API_TOKEN environment variable, which you set in your shell. connect never writes a token into a file. See coding agents and MCP server and CLI.

What the agent gets

The local server offers fifteen tools: five rule tools, eight context tools, get_budget and record_cost. The ones to start with:

  • get_standards: the rules for the files of the task, ordered and cut to a token budget.
  • get_rule: the full text of one rule, with its examples.
  • record_outcome: the agent reports whether it followed a rule.
  • propose_rule: the agent proposes a rule. It lands in .coflow/proposals/ and does nothing until a person merges it.
  • where_is and remember: facts about your system the agent looked up once.

Tell the agent once: “Before you change code, call get_standards for the files you will touch.”

Check a change

git diff | coflow check --diff -

Exit code 0 means clean and 1 means a required rule is broken. With --strict, exit code 2 means a rule in scope had no check run. A rule enforced by a tool that is not installed is reported as not run, never as passed. Rules that need a model review are listed as “not reviewed (no model)” until you configure a model.

See a rule proposal

Correct the agent in a session, for example “always pass a timeout to requests calls”. When it agrees the correction is a standing rule, it calls propose_rule and a file appears in .coflow/proposals/.

You can also capture corrections: coflow connect claude --capture (or cursor, gemini) installs the client’s end-of-session hook. For other clients, record one yourself with coflow lesson "always pass a timeout to requests calls". coflow inbox lists what was captured.

A proposal is never active. A person reviews it and merges the rule file in a pull request. Run coflow export after that so the agent files carry the new rule.

  • coflow context setup writes five questions about your system for a person to answer once.
