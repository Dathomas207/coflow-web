Agent Studio

Build, test and promote review agents that act only within limits people set.

Agents are flows

An agent is a flow: a small graph of typed steps in three swimlanes. The people lane holds approvals and decisions, the coding tools lane holds the tools and agents that read and change code, and the CoFlow lane holds rules, checks and records. Agent Studio adds versions, a sandbox, an autonomy ladder, bindings per repository, approvals before anything leaves CoFlow, and a full run history. Agent files in a repository keep working; each maps to a default flow. You can edit a draft as a diagram, an outline or a table of steps.

Agent templates

CoFlow ships 17 agent templates. Each is seeded for every organization at shadow with no binding, so it does nothing until a person binds it.

The autonomy ladder

LevelRuns onOutward actions
SandboxStored test cases onlyNone. No call to the code host.
ShadowReal eventsNone. The run records what it would have done.
AssistReal eventsEach action only after a person approves that exact content.
AutoReal eventsComments and check runs without a gate. Proposals, tickets and chat messages still need a person.
  • A run executes at the most restrictive of its pinned level, its binding’s level and the level published now, so a demotion applies to runs already in flight.
  • Promotion moves one level at a time. Demotion is immediate and needs no approval.
  • A kill switch pauses one agent or every agent in the organization. Paused runs stop before their next outward action.

The ceiling no setting can lift

No agent can merge, approve a pull request, push, force-push or bypass a check. These are refused as a step kind, an action, a level and a policy detail, and a flow that contains one does not load. No autonomy level, approval policy, policy profile or break-glass decision changes this. See agent safety.

Versions and promotion evidence

  • A draft can change. Publishing freezes it and needs a valid flow and a passing sandbox run on the exact content.
  • Above shadow, publishing also needs an approval from someone other than the last editor.
  • Promotion to shadow needs a passing sandbox run. Promotion to assist and auto also needs a harness run whose precision and recall meet the agent’s thresholds, and an approval under the promotion policy. A policy can also require a minimum shadow agreement.
  • In shadow, people mark each run’s would-be actions as agree or disagree, next to what reviewers actually did.
  • Rollback creates a new draft from an old version. History is never changed. A diff shows steps, rule selection and budget changes.

Pending actions and approvals

When a run reaches a person, it stores the exact content of the action and its hash. The approver confirms the hash they saw. A decision is refused if the content changed, the action expired, the person lacks the role or started the run themselves. Edits replace the draft and record who changed it; approval then applies to the new content. Before sending, CoFlow checks the hash again. Each step has an idempotency key, so a resumed run never sends twice.

Who reviews and who approves is set by approval policies for teams and organizations, with quorum and independence. See approvals.

Bindings and schedules

A binding attaches a published agent to a repository, optionally with paths and a branch pattern, and needs an approval. A binding can have a cron schedule; scheduled runs run at shadow at most and need the scheduled jobs to be set up.

Fleet, Needs you and traces

  • Fleet: every agent with its status, level and recent runs. Pause one with its switch, or all of them at once.
  • Needs you: approvals, actions waiting for a person and failed runs you can retry.
  • Traces: every run stores its step trace, findings and a cost record at every level. A person can retry a failed step without sending twice, or cancel a run.

Limits in this release

  • Studio runs on real pull requests are GitHub only. GitLab and Bitbucket get the plain review.
  • Ticket actions need a tracker connection that does not ship yet.
  • onboarding-guide needs the code host to report a first pull request, and its promotion stays refused until evaluations can score an explanation.
  • Under the planned billing model, sandbox, shadow and live runs use credits.
