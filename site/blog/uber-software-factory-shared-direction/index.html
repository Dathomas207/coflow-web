Uber’s software factory runs on context, skills and cost discipline.

Uber reports that more than 70% of its pull requests now involve coding agents. The lessons for smaller teams are about context, reusable skills and measuring cost per outcome.

By CoFlow · November 20, 2026 · 3 min read

On this pageWhat Uber publishedThree lessons that transferWhere CoFlow fitsApply it at your scale

Most of the debate about coding agents is about which one writes the best first draft. Uber’s engineering team has published a more useful question for anyone running agents across a real codebase: what does the system around the agents need, so that the work they produce is accurate, reviewable and affordable?

What Uber published

On August 27, 2026, Uber Engineering published Running a Software Factory Efficiently at Uber Scale, following a talk at the AI Engineer 2026 conference. Uber reports that more than 70% of its pull requests are now attributed to local or cloud agents. Between February and August 2026, weekly active users of its agent tools and weekly agent requests both grew several times over.

Total cost rose too, so Uber treated cost as an engineering problem. The post splits agent spend into a cost equation, measures each term and describes the four layers agent sessions run in, from raw sessions an engineer drives to fully managed agents. Uber reports that from peak to August, cost per 1,000 requests fell 34% and cost per session fell 52%.

Those numbers come from Uber’s environment, at Uber’s scale. They are evidence about Uber and should not be read as a forecast for any other team, including teams using CoFlow.

Three lessons that transfer

Context is infrastructure. Uber invested in shared organizational context that agents draw on, so each session does not start from zero. A ten-person team has the same problem at a smaller size: the conventions live in reviewers’ heads and reach the agent only when someone repeats them.

Reusable skills beat repeated prompts. Uber’s engineers package recurring work as skills that other agents reuse. The lesson for smaller teams is to stop rewriting the same instructions in every session and keep one reviewed version.

Measure cost per outcome. Uber tracks spend per request and per session alongside quality and completed work. Token spend alone says little; tokens per accepted change says a lot. DORA’s qualitative study of Google engineers found a related cost: time saved generating code often gets spent again on reviewing it.

Where CoFlow fits

CoFlow covers the context part of that system for teams that don’t have Uber’s platform team. Your reviewed rules, lessons and acceptance checks are compiled into a scoped instruction package for each task and delivered to the agents you already use:

  • Rules are reviewed before any agent receives them.
  • The instruction compiler selects the rules that apply to the task and keeps the exact package revision.
  • Acceptance checks and recorded outcomes let the team compare tokens, review rounds and repeat findings per accepted change.
  • MCP and export paths bring the package into Claude Code, Codex, Cursor and Copilot.

CoFlow is not Uber’s platform and does not do model routing or run agent infrastructure. It handles the reviewed engineering knowledge that should go into each task.

Apply it at your scale

Start with one repository and the correction your reviewers make most often. Turn it into a reviewed rule with an acceptance check, deliver it with the next tasks and record tokens, review rounds and whether the correction comes back. Add the next rule when the first one shows results.
