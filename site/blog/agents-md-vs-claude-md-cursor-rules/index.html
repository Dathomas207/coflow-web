AGENTS.md vs CLAUDE.md vs Cursor rules: one rule set for every coding agent.

Which instruction file Claude Code, Codex, Cursor and GitHub Copilot each read, how to stop them drifting apart, and why a hand-written AGENTS.md beats a generated one.

By CoFlow · November 20, 2026 · 3 min read

On this pageWho reads whatWhy the files drift apartA setup that stays in syncWhat belongs in the fileWhere CoFlow fits

Most teams now run more than one coding agent. One engineer uses Claude Code, another uses Cursor, CI runs Codex and Copilot reviews the pull request. Each agent looks for its instructions in a different place, and within a few weeks the files say different things.

Who reads what

AGENTS.md is the closest thing to a shared format. It is plain Markdown at the repository root, with optional nested files for subdirectories, and in December 2025 it was donated to the Linux Foundation’s Agentic AI Foundation as an open standard. The tools still differ in the details, so check each one’s documentation for the version you run:

Why the files drift apart

Drift starts with a good change. Someone updates the test command in AGENTS.md and forgets CLAUDE.md. A Cursor rule picks up a new error-handling convention that the Copilot file never hears about. Nobody reviews instruction files the way they review code, so the gap stays invisible until two agents produce two patterns for the same problem in the same week.

Precedence makes it worse. Claude Code reads AGENTS.md only when there is no CLAUDE.md, so a stale CLAUDE.md quietly wins over the file everyone thinks is in charge. A legacy .cursorrules left in the repository can do the same in older Cursor setups.

A setup that stays in sync

Keep one source of truth and make every other file point at it:

AGENTS.md                        # shared rules for every agent
CLAUDE.md                        # line 1: @AGENTS.md
.github/copilot-instructions.md  # Copilot-only notes
.cursor/rules/invoices.mdc       # globs: app/invoices/**
packages/billing/AGENTS.md       # one package's specifics

Put anything that needs scoping, such as rules that apply only to one directory, in the tool’s structured format or a nested AGENTS.md. Delete legacy files like .cursorrules once their content has moved. Review changes to all of these files in pull requests, with the same owners as the code they describe.

What belongs in the file

A March 2026 ETH Zurich study of context files in open-source repositories found that LLM-generated AGENTS.md files hurt agent performance. Write the file by hand, keep it short and include only what an agent can’t learn by reading the code:

  • Commands: how to install, test, lint and run one test file.
  • Boundaries: files and directories the agent must not edit, such as generated code and migrations already applied.
  • Non-obvious conventions: how tenant context is set, which shared components to reuse and which error format the API returns.
  • Definition of done: the checks that must pass before a change is ready for review.

Leave out style rules your linter already enforces and general advice the model already follows. Every line costs tokens on every task.

Where CoFlow fits

A single AGENTS.md works well for one repository with a few rules. It gets harder when rules apply to some paths and not others, when they need an owner and a reviewer, or when several repositories should share them. CoFlow keeps each rule as a reviewed, versioned entry with its scope and acceptance checks. Approved workspace exports return AGENTS.md content you can place in the repository, and the instruction compiler builds a task-specific package for agents connected over MCP.
