MCP security for coding agents: what to connect and how to lock it down.

Every MCP server you connect to a coding agent adds tools, permissions and text the model trusts. The main risks, from tool poisoning to over-scoped tokens, and the controls that address them.

By CoFlow · November 20, 2026 · 3 min read

On this pageWhat an MCP server addsThe main risksControls that workReview MCP servers like code

Connecting an MCP server to a coding agent takes one line of configuration. That line gives the agent new tools, whatever permissions the server’s credentials carry, and a block of text that the model reads and trusts on every turn.

What an MCP server adds

The Model Context Protocol lets agents call tools exposed by servers: a database, an issue tracker, a browser, a file system. The OWASP MCP Security Cheat Sheet points out that the model sees every tool description from every connected server in its context. One untrusted server can therefore influence how the agent uses all the others.

The main risks

Tool poisoning. A server hides instructions in a tool description, a parameter schema or a tool result. The user never sees them; the model does. A March 2026 study evaluated how seven major MCP clients defend against this, called tool poisoning the most prevalent and impactful client-side vulnerability, and found significant gaps in most of the clients tested.

Prompt injection through data. An issue comment, web page or file the agent reads can contain instructions. If the agent also holds a tool that sends data out, injected text can encode secrets into an ordinary-looking call, such as a search query.

Vulnerable servers. MCP servers are software, often young. Elastic Security Labs cites a March 2025 review of public MCP server implementations that found command injection flaws in 43% of those tested. Tool inputs come from model output, so a server that passes them to a shell trusts whatever the model was persuaded to send.

Over-scoped credentials. A server configured with an admin token gives the agent admin rights. A personal access token with access to every repository puts every repository in reach of a single injected instruction.

Silent changes. A server you approved last month can change its tool definitions in an update. The review you did no longer describes what is running.

Controls that work

  • Allowlist servers: keep a short list of approved servers per team, pinned to versions, and treat additions like a new dependency.
  • Read the tool descriptions: review the full description and schema text the model will see, not just the README.
  • Scope credentials to the task: read-only where possible, one repository or project, short-lived tokens and no shared admin keys.
  • Sandbox local servers: run them with the minimum file system access they need and no access to home directories or credential stores.
  • Keep humans on dangerous actions: require confirmation for writes, deletes, deployments and anything that sends data outside your systems.
  • Log tool calls: record which tool was called, with what arguments and on whose behalf, so an incident can be reconstructed.

Review MCP servers like code

Most teams track which MCP servers are in use the same way they used to track browser extensions: not at all. CoFlow’s MCP configuration catalog versions, validates, reviews and audits MCP server descriptors. An approved descriptor starts disabled, and turning it on requires a separate reviewed change. The catalog records configuration; it does not launch servers, connect to them or handle their secrets.

CoFlow’s own MCP server runs locally over stdio and calls the authenticated CoFlow API with a token from your secure environment. It can compile instructions, record outcomes and export the workspace. Approving rules stays a separate, authorized step, so an agent cannot approve its own guidance.
