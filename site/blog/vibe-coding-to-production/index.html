Blog/Vibe coding

Vibe coding gets you started. Production needs a system.

A vibe-coded prototype proves the idea. Before customers depend on it, it needs server-side authorization, reviewed migrations and rules your coding agents start every task with.

By CoFlow · November 20, 2026 · 3 min read

On this pageVibe coding was meant for throwaway projectsWhat breaks firstGive the agent your rules before it writes codeMeasure one recurring mistake

A vibe-coded prototype proves an idea works. It does not prove the app is safe to run on customer data, and the gap between those two is where most AI-built apps get into trouble. You can close that gap without giving up the speed that produced the prototype.

Vibe coding was meant for throwaway projects

Andrej Karpathy named the practice in a February 2025 post on X. He described accepting the model’s changes without reading the diffs, and said the approach was fine for throwaway weekend projects. Simon Willison drew the line a month later in Not all AI-assisted programming is vibe coding: once you review, test and understand the code an LLM writes, you are doing software development with an assistant.

The trouble starts when a prototype becomes a product without anyone deciding it should. A demo gets a login page, then a pilot customer, then a payment form. The code that was fine for a weekend is now holding someone else’s data.

What breaks first

The failures are predictable. They show up because the agent optimizes for the request in front of it, and nobody gave it the team’s rules.

AreaWhat it looks like in the prototypeWhat production needs
AuthorizationChanging an ID in the URL returns another customer’s record.Server-side authorization on every route, backed by tested database policies.
SecretsAn admin or service key ships in the browser bundle.Privileged keys stay on the server. The client gets a restricted key.
Schema changesTables are edited by hand in a dashboard.Reviewed migrations that run the same way in every environment, with a rollback plan.
ConsistencyEach agent session invents its own pattern for auth, errors and data access.Approved conventions that every session starts with.
VerificationSomeone clicked through the happy path once.Acceptance checks for failures and permission boundaries, run before each release.

None of this requires a rewrite. Most teams fix it one recurring problem at a time, as long as each fix sticks.

Give the agent your rules before it writes code

A fix sticks when the next agent session starts with it. In CoFlow, a rule records the intended behavior, where it applies, its exceptions, the evidence behind it and the checks that prove it. A reviewer approves it before any agent sees it. Here is an illustrative rule for the most common prototype failure:

Rule:        Tenant-scoped invoice access
Applies to:  app/invoices/**   (postgresql, fastapi)
Behavior:    Resolve the organization from the verified session, set it in
             the query transaction and require project authorization.
             An invoice ID alone never grants access.
Exception:   The nightly billing export, which runs under the reviewed
             export role.
Evidence:    The review comment that caught an unscoped invoice lookup.
Acceptance:  pass  Tenant A reads its own invoice
             deny  Tenant A requests Tenant B's invoice ID   -> 404
             deny  Request with no organization context      -> 401

Once approved, the instruction compiler adds the rule to the instruction package for any task that touches those paths and records why it was selected. If a required rule would not fit the budget, or conflicts with another declared rule, compilation blocks rather than quietly dropping it. Workflow Studio can capture the prototype’s flows and export them as Playwright checks.

CoFlow delivers the rule to the agent. Your application, database and CI still enforce it and run the checks.

Measure one recurring mistake

Pick a mistake your reviewers keep correcting. Write it as a rule, give it to the next tasks that touch the affected code and count how often review catches it again. Track review rounds, time to an accepted change and total model tokens, including retries, against similar tasks from before the rule existed.

If the mistake stops coming back and review gets shorter, write the next rule. If it doesn’t, the rule needs sharper wording or a better acceptance check.
