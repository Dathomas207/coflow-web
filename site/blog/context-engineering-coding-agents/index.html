Context engineering for coding agents: fewer tokens, better changes.

More context often makes coding agents worse and costs more. How to give each task the rules it needs, measure token use per accepted change, and stop pasting the same instructions into every session.

By CoFlow · November 20, 2026 · 3 min read

On this pageWhat context engineering means for coding agentsWhy more context backfiresFive practices that cut tokensMeasure tokens per accepted change

The common fix for a coding agent that gets things wrong is to give it more: a longer instruction file, the whole architecture document, every convention the team has ever written down. It feels safe. It usually makes the output worse and the bill higher.

What context engineering means for coding agents

In Context Engineering for Coding Agents, a February 2026 Thoughtworks memo on martinfowler.com, the author quotes Thoughtworks colleague Bharani Subramaniam’s definition: context engineering is curating what the model sees so that you get a better result. For a coding agent, that covers the instruction files, the rules and skills it loads, the tool descriptions from connected servers, the files it reads and the conversation so far.

All of it competes for the same window, and all of it is billed on every turn.

Why more context backfires

Agents resend their context on every step of a task. A paragraph that adds nothing still costs tokens on every tool call, and in a long session most of the bill is input rather than output.

Irrelevant context also dilutes the instructions that matter. When the rule about tenant-scoped queries sits between fifty lines about naming conventions and a deployment runbook, the model gives it less weight. Teams see this as an agent that follows a rule on Monday and ignores it on Wednesday, with nothing changed except what else was in the window.

Five practices that cut tokens

Scope rules to paths and tasks. A rule about invoice queries belongs in tasks that touch app/invoices/. Cursor rule globs, Copilot applyTo patterns, nested AGENTS.md files and path-scoped CLAUDE.md rules all exist for this.

Keep the always-loaded file short. The root instruction file loads on every task. Limit it to commands, hard boundaries and the definition of done. Move everything else to scoped files the agent loads only when relevant.

Delete what the code already says. If the linter enforces it, the formatter fixes it or the agent can read it from a neighboring file, it doesn’t need an instruction.

Use small, targeted tool results. Every connected MCP server adds its tool descriptions to the context. Connect the servers a task needs, and prefer tools that return the relevant record over tools that return the whole table.

Start long tasks fresh. When a session has drifted, summarize what is settled and start a new one with that summary and the task’s rules. A clean window often beats a long history.

Measure tokens per accepted change

Raw token counts reward doing less. The useful number is total tokens, including retries and failed attempts, per change a reviewer accepts. Measure it alongside review rounds and repeat findings, on similar tasks, with the same model.

MetricWhat it tells you
Total tokens per accepted changeCost of getting to a change you can merge, retries included
Review rounds per changeWhether the agent started with the right rules
Repeat findingsWhether a correction made last week is still being made
Instruction size per taskHow much of the window goes to rules before work starts

CoFlow is built for the instruction part of this. The instruction compiler selects approved rules by repository, path, task type and technology, records why each was included, and keeps optional context within a budget. Required rules are never dropped to fit; compilation blocks instead. CoFlow’s size estimate is a conservative byte count, not an exact token count, so measure actual model usage separately when you compare tasks in a pilot.
