A login screen is not a data boundary.

How to enforce tenant isolation with PostgreSQL row-level security: policies that fail closed, the roles and views that bypass them, and the negative tests that prove them.

By CoFlow · November 20, 2026 · 4 min read

On this pageWrite policies that fail closedKnow what bypasses RLSTest the requests that must failGive the requirement to the coding agent

Your new internal tool signs users in and the happy path works. Then someone changes an invoice ID in a request and gets another team’s invoice back. Authentication established who they were. Nothing checked what they were allowed to see.

Prototypes built quickly with AI often stop at the login screen. Authorization has to hold on every path into the data, including the ones nobody clicked during the demo: exports, background jobs, admin screens and direct API calls.

Write policies that fail closed

PostgreSQL row-level security (RLS) attaches the tenant check to the table, so a forgotten WHERE clause in application code can’t leak rows. Supabase’s production checklist lists RLS on every table as a baseline. Turning it on is the start. The policy has to express your access model:

alter table invoices enable row level security;
alter table invoices force row level security;

create policy tenant_isolation on invoices
  using (
    organization_id = current_setting('app.organization_id', true)::uuid
  )
  with check (
    organization_id = current_setting('app.organization_id', true)::uuid
  );

The true argument makes current_setting return null when no organization is set, so a request with missing context matches no rows. That is the behavior you want: fail closed. with check stops an update or insert from moving a row into another tenant.

The application sets the organization once per transaction, from the verified session and never from a request header or body:

begin;
-- third argument true: the setting ends with this transaction
select set_config('app.organization_id', $1, true);
-- queries for this request
commit;

The transaction-local flag matters with connection pooling. A session-level setting stays on the connection and travels to whichever request borrows it next.

Know what bypasses RLS

Most RLS failures in fast-built apps come from something that skips the policy entirely, rather than a bad policy:

  • Table owners and superusers: superusers and roles with BYPASSRLS skip every policy. Table owners skip them too unless the table uses FORCE ROW LEVEL SECURITY. Run the app as a restricted role that owns nothing.
  • Views: by default a view runs with its owner’s privileges. On PostgreSQL 15 and later, create views with security_invoker = true so the caller’s policies apply.
  • Security definer functions: they run as the function owner. Treat each one as an authorization boundary and review it that way.
  • Privileged API keys: Supabase’s service_role key bypasses RLS. It belongs on the server, never in a browser bundle or a mobile app.

Test the requests that must fail

A test suite that only proves users can see their own data proves half the boundary. These are the cases worth automating:

  • A user in organization A requests organization B’s record by ID.
  • A valid user requests a project they have no permission for.
  • A request arrives with missing or stale tenant context.
  • An update or delete targets another tenant’s rows.
  • A background job processes work for several tenants in one run.
  • A pooled connection is reused right after another tenant’s transaction.

Run them as the real application role against real PostgreSQL. A test that connects as the table owner passes even when the policy is wrong, and an SQLite test database proves nothing about PostgreSQL policies.

-- Run as the restricted runtime role, not the table owner
set role app_user;

-- Signed in as org A, reaching for org B
begin;
select set_config('app.organization_id', :'org_a', true);
select count(*) from invoices
  where organization_id = :'org_b';         -- expect 0
update invoices set amount = 0
  where organization_id = :'org_b';         -- expect UPDATE 0
rollback;

-- No organization context at all
begin;
select count(*) from invoices;              -- expect 0
rollback;

Give the requirement to the coding agent

Once the team has agreed on the pattern, write it down as a reviewed CoFlow rule scoped to the repositories and paths that touch tenant data. Attach the denial cases above as acceptance checks. Every agent task that changes a protected route, migration or job then starts with the approved pattern and the tests it has to pass.

CoFlow carries the requirement into the task. It does not install or verify RLS in your application; your database and test runner do that. The RLS guide covers how CoFlow isolates its own data and where your policies take over.

When review catches an unscoped query, turn it into a rule. The next agent should start from the access pattern your team already approved.
