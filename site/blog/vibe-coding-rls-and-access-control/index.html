Production security

A login screen is not a data boundary.

Why tenant isolation and RLS need explicit policies, negative tests and shared engineering context.

By CoFlow · November 20, 2026 · 2 min read

In this articleMake the data boundary explicitTest the requests that must failKeep that requirement available to the coding agent

Your new internal tool signs users in. The happy path works. Then someone changes an invoice ID in a request. Can they see another team’s data?

That is the kind of question a convincing demo can leave unanswered. Authentication establishes who is making a request. Authorization decides what that identity can access, through every path into the data.

Make the data boundary explicit

Supabase’s production security checklist calls for RLS and appropriate policies, alongside account protection, authentication settings and threat review. Turning on a setting is only the beginning: the policies have to express your application’s access model.

For a multi-tenant application, define the organization and project boundary, where trusted membership comes from, and which runtime roles can bypass normal restrictions. Review background jobs, exports and administrative paths too.

Test the requests that must fail

  • A user in organization A requests organization B’s record.
  • A valid user has no permission for the requested project.
  • A request has missing or stale tenant context.
  • A background job processes work for multiple tenants.
  • A pooled connection is reused after another tenant’s transaction.

Test with the real application role and the actual database policies. Include updates and deletes as well as reads. A test running as a privileged database owner can miss a boundary that the production role depends on.

Keep that requirement available to the coding agent

In CoFlow, turn the reviewed requirement into scoped guidance for the repositories and tasks that touch tenant data. Pair it with positive and negative acceptance checks, then record what happened against the instruction package used.

CoFlow’s RLS guide explains its own PostgreSQL isolation design and the distinction between CoFlow’s controls and your application’s policies. CoFlow can carry your RLS requirements into a task; it does not automatically install or verify RLS in a customer application.

When a review catches an unscoped query, preserve the lesson. The next agent should start with the team’s approved access pattern rather than rediscovering the same boundary.
