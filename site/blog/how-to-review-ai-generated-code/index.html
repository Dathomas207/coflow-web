How to review AI-generated code: a checklist for pull requests.

AI-generated code fails in different ways from human code. A pull request checklist ordered by cost of error: intent, invented APIs and packages, security defaults, tests and duplication.

By CoFlow · November 20, 2026 · 3 min read

On this pageWhy generated code needs its own checklistThe checklistTurn repeat findings into rules

A pull request from a coding agent usually looks finished. The names are sensible, the comments are tidy and the happy path works. That polish is the problem: the defects that matter are rarely the ones that look wrong.

Why generated code needs its own checklist

Research on AI-generated code keeps finding the same pattern. A 2024 systematic literature review cites Pearce et al. (2022), who found that 40% of the Copilot suggestions they tested contained vulnerabilities, and Perry et al. (2023), who found that users trusted AI-generated code more than their own. A 2025 analysis of 576,000 generated code samples found that models recommended packages that do not exist in 5.2% of samples from commercial models and 21.7% from open-source models.

Generated code also fails differently from human code. A human who misunderstands the task usually writes something visibly incomplete. A model writes complete, confident code for a slightly different problem.

The checklist

Work through it in this order. It runs from the most expensive mistakes to the cheapest, so a reviewer short on time covers what matters first.

1. Intent. Read the ticket, then the diff. Does the change solve the problem that was asked, or a nearby one that was easier? Check the edge case named in the ticket, not only the example.

2. Scope of the diff. Look at git diff --stat before reading any code. A one-line bug fix that touches twelve files needs an explanation. Watch for edits to unrelated files, reformatted code, deleted tests and loosened assertions.

3. Invented APIs and packages. Confirm every new import exists, is the package you think it is and is spelled correctly. Attackers register package names that models tend to invent, a practice known as slopsquatting. Check that every method called exists in the version pinned in your lockfile.

4. Security defaults. Models reproduce the most common pattern in public code, which is often the unsafe one. Anywhere the change touches user input, authentication, database queries, files, shell commands or outbound URLs, read as an attacker:

  • Is every query scoped to the current tenant and parameterized?
  • Is authorization checked on the server, on this route?
  • Are secrets read from the environment, and kept out of logs and error messages?
  • Is user-supplied input kept out of shell commands, file paths and redirect URLs?

5. Error handling. Generated code often catches every exception and carries on, or returns a default that hides a failure. Check what happens when the database is down, the input is malformed or the user lacks permission.

6. Tests that test something. Read the assertions. A test that mocks the function under test, asserts only that no exception was raised, or was edited to match new behavior proves nothing. Ask for at least one test that must fail, such as a denied request.

7. Duplication. Agents rarely search the codebase before writing a helper. Check whether the new utility, component or query already exists. Two date formatters cost nothing today and diverge within a quarter.

Turn repeat findings into rules

Keep a note of which checklist items you flag. When the same finding shows up for the third time, it is no longer a review comment. It is a rule the agent should have had before it started.

In CoFlow, that finding becomes a proposed rule with the review comments as evidence. Once approved, it goes into the instruction package for every task touching the same paths, with an acceptance check that catches it if it comes back. Review agents can then check new pull requests against the approved rules, and a human still decides.

Track how often each finding recurs after its rule is approved. A finding that keeps coming back means the rule needs clearer wording or a sharper check.
